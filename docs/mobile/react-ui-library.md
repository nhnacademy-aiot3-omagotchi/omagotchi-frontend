# 오마고치 학습 서비스 게임 UI 프레임워크 도입 검토안

- 작성일: 2026-08-12
- 상태: 주말 검토용 초안 — 구현 확정 아님
- 실행 가이드: [React 게임 UI 도입 실행 체크리스트](react-ui-adoption-checklist.md)

## 1. 문서 목적

현재 오마고치는 Spring Boot 기반 웹 서비스에 React 홈 화면을 결합한 상태다.
이 문서는 기존 코드를 버리지 않으면서 학습 서비스를 게임처럼 느끼게 만들 수 있는
프레임워크와 적용 순서를 검토하기 위해 작성했다.

핵심 원칙은 다음과 같다.

- 학습 기능이 중심이고 게임은 학습 행동에 대한 피드백이어야 한다.
- React를 서비스 UI의 중심으로 유지한다.
- 라이브러리를 한꺼번에 추가하지 않는다.
- PC 화면을 기준으로 완성한 뒤 모바일에서 구조가 깨지지 않게 대응한다.
- 백엔드가 연결되지 않은 데이터는 임의로 만들어 표시하지 않는다.
- 흰 카드 나열, 의미 없는 영문 배지, 과도한 둥근 모서리 같은 전형적인 생성형 UI를 피한다.

## 2. 현재 구조와 목표 구조

### 현재 구조

```text
Spring Boot
├── 인증과 서버 라우팅
├── Thymeleaf HTML
├── 정적 CSS·JavaScript
└── React 홈 화면과 오버레이 틀
```

### 권장 목표 구조

```text
Spring Boot
├── 인증
├── 출석·학습·기수·커뮤니티 API
└── DB

React
├── 홈과 HUD
├── Radix UI 기반 공통 조작 컴포넌트
├── Motion 기반 상호작용 피드백
└── Phaser 기반 공간 화면 — 필요할 때만
```

React는 화면과 데이터 표시를 담당하고, Spring Boot는 실제 데이터와 권한을 담당한다.
Phaser는 서비스 전체가 아니라 캐릭터가 이동하는 공간에만 제한적으로 사용한다.

## 3. 프레임워크 후보 판단

| 도구 | 역할 | 도입 시점 | 판단 |
|---|---|---:|---|
| React | 서비스 UI와 상태 표현 | 현재 | 유지 |
| Radix UI | Dialog, Tabs, Tooltip 등 접근 가능한 동작 | 1차 | 권장 |
| Motion | 오버레이, 경험치, 보상 등의 미세 애니메이션 | 1차 | 권장 |
| Storybook | 컴포넌트를 페이지와 분리해 비교·검증 | 1차 또는 2차 | 권장 |
| Phaser | 캐릭터 이동, 방, NPC, 미니게임 | 공간 기획 확정 후 | 조건부 권장 |
| XState | 복잡한 타이머·캐릭터 상태 전이 | 상태가 복잡해진 후 | 보류 |
| Rive | 벡터 기반 인터랙티브 애니메이션 | 아트 방향 변경 시 | 현재는 제외 |
| React Native | 별도 네이티브 앱 UI | 장기 검토 | 현재는 제외 |

### 결론

첫 적용 후보는 **Radix UI + Motion + Storybook**이다.
Phaser는 공간 기능 요구사항과 에셋이 확정된 후 별도 프로토타입으로 판단한다.

## 4. 도구별 적용 범위

### 4.1 React

React가 계속 담당할 화면:

- 홈 HUD
- 학습 타이머
- 캐릭터 상태
- 경험치와 레벨
- 퀘스트·업적·랭킹
- 내 정보
- 학습 기록
- 출석 현황
- 기수·커뮤니티·설정
- BGM과 재실 확인

React 전환의 목표는 모든 코드를 JSX로 옮기는 것이 아니다. 상태 변화가 있는 UI부터
컴포넌트화하고, 서버 템플릿은 초기 진입과 인증 경계로 유지할 수 있다.

### 4.2 Radix UI

Radix UI는 스타일이 없는 조작 뼈대로만 사용한다.

| 현재 기능 | 적용 후보 |
|---|---|
| 진행·내 정보·커뮤니티 오버레이 | Dialog |
| 퀘스트·랭킹 전환 | Tabs |
| 도움말 | Accordion |
| 퇴실·로그아웃 확인 | Alert Dialog |
| 메뉴 설명 | Tooltip |
| BGM 음량 | Slider |
| 설정 선택 항목 | Switch, Select |

Radix 기본 디자인을 가져오는 것이 아니라 키보드 조작, 포커스 이동, ARIA 처리만 맡기고
시각 디자인은 오마고치 CSS로 직접 작성한다.

참고: [Radix UI 공식 문서](https://www.radix-ui.com/primitives/docs/overview/introduction)

### 4.3 Motion

Motion은 짧은 조작 피드백에만 사용한다.

권장 효과:

- 버튼을 누를 때 1~2px 내려가는 반응
- 오버레이가 4~8px 이동하며 나타나는 효과
- 경험치 바 증가
- 레벨 숫자 변경
- 퀘스트 완료 도장
- 출석 완료 표시
- 캐릭터 말풍선의 등장과 퇴장
- 보상 아이템 획득

피해야 할 효과:

- 모든 카드가 순서대로 날아오는 애니메이션
- 긴 페이지 전환
- 배경의 지속적인 움직임
- 사용자가 기다려야 하는 연출
- 모바일 성능을 떨어뜨리는 과도한 블러와 그림자

`prefers-reduced-motion` 설정을 존중하고, 애니메이션이 없어도 기능이 정상 작동해야 한다.

참고: [Motion for React 공식 문서](https://motion.dev/docs/react)

### 4.4 Storybook

Storybook에는 완성된 페이지가 아니라 반복해서 쓰는 UI를 등록한다.

초기 등록 대상:

- `GameButton`
- `GamePanel`
- `GameDialog`
- `GameTabs`
- `StatRow`
- `QuestRow`
- `RankingRow`
- `Toast`
- `ProgressBar`
- `CharacterBubble`

각 컴포넌트에는 아래 상태를 준비한다.

```text
기본 / hover / focus / disabled / loading / empty / error / long-text
```

PC, 태블릿, 모바일 뷰포트를 같은 자리에서 비교한다. 서버가 없어도 mock 데이터로 UI
상태를 확인하되 실제 앱에서는 백엔드 데이터와 명확히 구분한다.

참고: [Storybook UI 테스트 공식 문서](https://storybook.js.org/docs/writing-tests)

### 4.5 Phaser

Phaser 적용 후보는 `공간` 화면 하나다.

가능한 기능:

- 캐릭터 이동
- 책상과 학습 자리 선택
- 다른 사용자 캐릭터 표시
- 방 입장과 퇴장
- NPC 상호작용
- 작은 보상형 미니게임

구조 예시:

```text
React SpacePage
├── 상단 방 정보와 나가기 버튼
├── Phaser Canvas
└── React 채팅·사용자 목록·설정 패널
```

Phaser가 타이머, 채팅, 입력 폼, 설정까지 담당하게 만들지 않는다. Canvas 외부의 일반 UI는
React가 담당해야 접근성과 반응형 관리가 쉽다.

참고: [Phaser 공식 문서](https://docs.phaser.io/)

### 4.6 XState

다음 상태가 실제로 복잡해질 때만 검토한다.

```text
캐릭터: idle → happy → studying → tired → sleeping → levelUp
타이머: idle → running → paused → completing → saved → error
```

현재처럼 상태가 단순한 단계에서 도입하면 코드가 오히려 복잡해질 수 있다. 백엔드 저장,
복구, 네트워크 오류, 애니메이션 전환이 함께 얽힐 때 도입 여부를 다시 판단한다.

참고: [XState 공식 문서](https://stately.ai/docs)

## 5. 게임다운 학습 흐름

게임처럼 보이는 것보다 학습 행동이 게임 진행과 연결되는 것이 중요하다.

```text
입실
  ↓
오늘의 퀘스트 확인
  ↓
집중 타이머 시작
  ↓
학습 세션 완료
  ↓
경험치·아이템 지급
  ↓
캐릭터 반응 또는 성장
  ↓
학습 기록 저장
```

### 화면 역할

| 화면 | 게임 내 의미 | 실제 서비스 기능 |
|---|---|---|
| 홈 | 캐릭터 방 | 오늘 상태와 빠른 실행 |
| 진행 | 퀘스트 북 | 목표·업적·랭킹 |
| 내 정보 | 상태창 | 계정·학습·캐릭터 정보 |
| 학습 기록 | 모험 일지 | 세션 기록과 통계 |
| 기수 | 길드 | 소속과 구성원 |
| 공간 | 학습실 맵 | 재실·스터디룸 |
| 커뮤니티 | 게시판 | 공지와 자유 글 |
| 출석 | 일일 접속 | 입실·퇴실·연속 출석 |
| 설정 | 시스템 메뉴 | 계정과 환경 설정 |

## 6. 디자인 시스템 초안

### 시각 원칙

- 기본색은 초록, 종이색, 검정, 흰색의 4계열로 제한한다.
- 강조색은 성공·경고·위험처럼 의미가 있을 때만 사용한다.
- 픽셀 폰트는 제목과 숫자에 사용하고 본문은 읽기 좋은 시스템 폰트를 검토한다.
- 패널은 하나의 큰 상태창 안에서 선과 간격으로 구분한다.
- 모든 항목을 독립적인 둥근 카드로 만들지 않는다.
- 버튼 높이, 테두리 굵기, 패널 간격을 토큰으로 통일한다.

### CSS 토큰 예시

```css
:root {
  --game-bg: #1fbe79;
  --game-panel: #23875b;
  --game-panel-dark: #176b46;
  --game-paper: #f6fff9;
  --game-ink: #10241b;
  --game-line: rgba(255, 255, 255, 0.24);

  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --space-4: 16px;
  --space-5: 24px;

  --radius-control: 8px;
  --radius-panel: 12px;
  --control-height: 44px;
}
```

### 피해야 할 생성형 UI 특징

- 필요 이상으로 많은 설명문
- `PLAYER PROFILE`, `QUICK PLAYER` 같은 의미 없는 영문 라벨
- 모든 요소에 아이콘을 하나씩 추가
- 여러 색상의 카드 그리드
- 과한 그라데이션과 유리 효과
- 큰 빈 공간을 디자인으로 착각하는 구성
- 동일한 정보의 중복 표시

## 8. 백엔드와 프런트엔드 경계

### 백엔드가 결정해야 하는 값

- 사용자 ID와 권한
- 실제 학습 시간
- 세션 완료 여부
- 출석·퇴실 시간
- 경험치와 레벨
- 퀘스트 완료와 보상
- 랭킹
- 기수 소속
- 재실 상태
- 게시글과 댓글

### 프런트엔드가 담당할 값

- 현재 열린 오버레이
- 선택된 탭
- 입력 중인 검색어
- 애니메이션 상태
- 임시 폼 상태
- 서버 응답의 로딩·성공·실패 표시

### 금지할 임시 처리

- 실제 랭킹처럼 보이는 샘플 사용자
- 서버 저장이 되지 않는데 완료된 것처럼 표시하는 보상
- localStorage 값을 최종 데이터로 간주
- 네트워크 실패를 성공으로 처리

Storybook과 개발 미리보기에서는 mock 데이터를 사용할 수 있지만 `Mock`임을 코드와 화면
환경에서 구분한다.

## 9. 단계별 적용 계획

### 0단계 — 주말 결정

- 게임의 핵심 반복 행동을 한 문장으로 정한다.
- 공간 기능에 실제 이동이 필요한지 결정한다.
- 픽셀 디자인 참고 화면 3개를 선정한다.
- PC 기준 너비와 모바일 최소 너비를 정한다.
- Phaser 도입 여부는 보류 상태로 둔다.

### 1단계 — UI 기반 정리

- 디자인 토큰 작성
- `GameButton`, `GamePanel`, `GameDialog`, `GameTabs` 제작
- Storybook에 컴포넌트 상태 등록
- 기존 오버레이 하나를 Radix Dialog로 시험 전환
- 기존 탭 하나를 Radix Tabs로 시험 전환

완료 기준:

- 키보드로 열기·이동·닫기가 가능하다.
- PC와 모바일에서 같은 정보 구조를 유지한다.
- 기존 기능이 깨지지 않는다.

### 2단계 — 게임 피드백 추가

- Motion으로 버튼, 오버레이, 경험치 애니메이션 적용
- 퀘스트 완료와 출석 완료 연출 제작
- `prefers-reduced-motion` 대응
- 저사양 모바일에서 지속 애니메이션 제거

### 3단계 — 백엔드 연결

- 인증 사용자 조회
- 타이머 저장과 복구
- 학습 기록
- 출석
- 경험치·퀘스트
- 랭킹·기수·재실·커뮤니티 순으로 연결

API 연결 전에는 로딩, 빈 상태, 실패 상태 디자인만 준비한다.

### 4단계 — 공간 프로토타입

- 별도 브랜치에서 Phaser로 방 하나 제작
- 캐릭터 한 명 이동
- 책상 선택
- React 패널과 이벤트 연결
- PC와 모바일 성능 측정

프로토타입 결과가 좋을 때만 본 프로젝트에 합친다.

### 5단계 — 앱 배포 검토

- HTTPS 웹 배포
- PWA 적용
- 모바일 설치 경험 검증
- 필요하면 Capacitor로 Android 패키징
- Android 안정화 후 iOS 검토

## 10. Phaser 도입 결정 기준

아래 질문 중 3개 이상이 `예`일 때 Phaser 프로토타입을 진행한다.

- 캐릭터가 공간 안에서 자유롭게 이동해야 하는가?
- 충돌 영역이나 상호작용 오브젝트가 필요한가?
- 여러 프레임의 스프라이트 애니메이션이 필요한가?
- 맵과 카메라 이동이 필요한가?
- 미니게임이 실제 핵심 기능인가?
- 같은 방에 있는 다른 사용자를 공간적으로 표현해야 하는가?

단순히 캐릭터가 움직이고 클릭에 반응하는 수준이라면 React + CSS + Motion으로 충분하다.

---

## 11. 위험 요소와 중단 기준

### 위험 요소

- 라이브러리 도입이 실제 UI 통일보다 목적이 되는 문제
- React와 기존 JavaScript가 같은 DOM을 동시에 제어하는 문제
- Phaser Canvas와 React 오버레이의 좌표·포커스 충돌
- 백엔드 확정 전 프런트 상태가 과도하게 복잡해지는 문제
- 픽셀 폰트 때문에 모바일에서 글자가 잘리는 문제
- 애니메이션이 학습 흐름을 방해하는 문제

### 중단 기준

- 공통 컴포넌트보다 예외 CSS가 더 많이 생긴다.
- 기존 기능을 유지하기 위해 이중 상태 관리가 필요하다.
- Phaser 프로토타입이 일반 DOM보다 조작성이 나쁘다.
- 모바일에서 30fps 이하로 체감된다.
- 게임 연출 때문에 학습 시작까지 단계가 늘어난다.

이 경우 새 도구 도입을 중단하고 React와 CSS만으로 돌아간다.

## 13. Index와 Home 적용 구상

정확한 픽셀 단위 레이아웃을 확정하기 전에 각 화면의 역할과 정보 우선순위를 먼저
고정한다. `index`와 `home`에 같은 게임 UI를 무조건 반복하지 않는다.

### 13.1 우리 서비스의 Index 적용 방향

현재 Index의 초록 배경, 픽셀 글꼴, 오마고치 캐릭터 중심 분위기는 유지한다. Index를 새
랜딩페이지 템플릿으로 교체하지 않고, **오마고치가 학습 서비스라는 사실과 시작 경로를
더 분명하게 만드는 방향**으로 적용한다.

Index에서 보여줄 내용은 다음으로 제한한다.

- 오마고치 로고와 대표 캐릭터
- `공부한 시간만큼 캐릭터가 성장한다`는 서비스 핵심 문장
- 로그인·회원가입 또는 학습 시작 버튼
- 입실, 집중, 기록, 성장으로 이어지는 실제 서비스 흐름
- 현재 Home 화면을 기반으로 한 짧은 서비스 미리보기

랭킹, 커뮤니티, BGM, 재실 인원 같은 로그인 이후 기능은 Index에서 미리 구현하거나
전부 설명하지 않는다. Index는 기능 목록이 아니라 서비스의 핵심 경험을 보여주는 곳으로
사용한다.

### 13.2 Index에서 실제로 적용할 동작

#### 비로그인 사용자

- 대표 버튼은 로그인 또는 시작하기로 연결한다.
- 회원가입은 보조 행동으로 둔다.
- 캐릭터를 누르면 짧은 말풍선이나 학습 반응을 한 번 보여준다.
- 이용 방법은 긴 본문 대신 필요한 경우에만 Dialog 또는 Accordion으로 연다.

#### 로그인 사용자

- 초기 캐릭터 설정이 끝나지 않았으면 캐릭터 선택으로 이동한다.
- 오늘 입실이 필요하면 `/check-in`으로 이동한다.
- 이미 입실했으면 Home으로 바로 이동한다.
- Index에서 Home 기능을 중복 실행하지 않는다.

#### 캐릭터 미리보기

- 현재 사용하는 실제 오마고치 에셋을 재사용한다.
- 대기 상태와 공부 상태 정도만 짧게 보여준다.
- 캐릭터를 별도의 3D·벡터 스타일로 바꾸지 않는다.
- Index 미리보기 상태와 로그인 후 실제 캐릭터 데이터는 구분한다.

### 13.3 Index에 프레임워크를 적용하는 범위

| 적용 대상 | 사용 도구 | 우리 서비스에서의 사용 방식 |
|---|---|---|
| 로그인 상태별 시작 버튼 | React | 세션 상태에 맞게 이동 경로 변경 |
| 캐릭터 반응 | Motion 또는 CSS | 클릭과 대기 상태에 짧은 반응만 적용 |
| 이용 방법 | Radix Dialog/Accordion | 필요할 때만 설명 표시 |
| Home 미리보기 | React | 실제 공통 컴포넌트를 읽기 전용으로 재사용 |
| 반응형 | CSS | 같은 정보 순서를 유지하며 모바일에서 세로 정렬 |

Index에는 Phaser를 사용하지 않는다. 캐릭터 한 마리의 반응을 위해 게임 엔진을 로드하는
것은 현재 서비스 규모에 비해 과하다.

### 13.4 현재 UI를 유지하면서 Octodoro와 구분하는 방법

현재 UI가 마음에 든다면 전체 색상과 배치를 다시 만들 필요는 없다. 문제는 완성도가
아니라 **초록색 픽셀 학습 서비스라는 인상이 Octodoro와 겹치는 것**이므로, 구조를
갈아엎기보다 오마고치만의 시각 언어를 추가한다.

#### 유지할 것

- 초록색 중심 색상
- 픽셀 캐릭터와 픽셀 제목 글꼴
- 단순한 타이머 중심 화면
- 현재 메뉴와 오버레이의 기본 정보 구조
- PC와 모바일에서 이어지는 같은 서비스 경험

#### 오마고치만의 특징으로 강화할 것

- 나뭇가지에 앉은 캐릭터와 머리 위 말풍선을 대표 장면으로 사용
- 학습 시간에 따라 캐릭터 표정·자세·주변 소품이 달라지는 성장 표현
- 출석은 일반 달력보다 도장 또는 학습 흔적의 느낌을 사용
- 학습 기록은 일반 통계 카드가 아니라 캐릭터의 성장 일지처럼 표현
- 기수와 재실 기능은 실제 실습실·동료 학습이라는 서비스 고유 요소로 강조
- 경험치와 레벨은 장식이 아니라 실제 학습 결과와 직접 연결
- 알림 문구는 일반 생산성 앱 문구보다 캐릭터가 사용자에게 말하는 방식으로 작성

#### Octodoro와 닮아 보일 수 있어 줄일 것

- 로고 아래에 동일한 크기의 메뉴 버튼을 길게 나열하는 인상
- 단색 배경 위에 둥근 박스만 반복하는 구성
- 영문 라벨이 붙은 파란색·초록색 게임 모달
- 퀘스트, 랭킹, 설정 화면에서 비슷한 탭과 카드 구조를 그대로 반복
- 문어 또는 다른 서비스의 보상·재화 체계를 연상시키는 장식

차별화 비율은 `현재 UI 80% 유지 + 오마고치 고유 표현 20% 강화` 정도로 잡는다.
색상을 갑자기 바꾸거나 모든 화면을 새로 디자인하는 방식은 권장하지 않는다.

### 13.5 Index에서 먼저 보여줄 오마고치 정체성

Index의 첫 장면에서 다음 관계가 바로 보여야 한다.

```text
사용자의 학습
      ↓
시간과 기록 축적
      ↓
오마고치의 반응과 성장
      ↓
기수·실습실 동료와 함께 이어가는 학습
```

따라서 Index는 Octodoro처럼 `타이머 서비스`를 먼저 보여주는 것이 아니라, **학습 기록으로
함께 성장하는 캐릭터 서비스**를 먼저 보여준다. 타이머는 그 경험을 만드는 기능 중 하나로
설명한다.

### 13.6 Home의 역할

Home은 로그인 후 매일 사용하는 **게임형 학습 조작 화면**이다.

사용자가 Home에서 바로 확인하거나 실행할 내용:

1. 캐릭터의 현재 상태
2. 오늘의 학습 시간과 타이머
3. 현재 레벨과 경험치
4. 오늘 해야 할 다음 행동
5. 출석, 기록, 공간 등 주요 기능 진입

Home은 정보 소개가 아니라 조작이 목적이므로 긴 설명문을 넣지 않는다.

### 13.7 Home 데스크톱 구상

```text
┌─────────────────────────────────────────────────────────────┐
│                        Omagotchi                            │
│ [도움말][진행][내 정보][기수][기록][공간][커뮤][설정]       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│                      01:00:00                               │
│                     [시작/정지]                              │
│                                                             │
│                    [말풍선]                                 │
│                    [캐릭터]                                 │
│                                                             │
├─────────────────────────────────────────────────────────────┤
│ 채팅 입력 │ Lv.12  캐릭터명  [경험치────────] │ 빠른 실행  │
└─────────────────────────────────────────────────────────────┘
```

기본 화면은 캐릭터와 타이머가 중심이다. 퀘스트, 랭킹, 커뮤니티를 홈 바닥에 전부 노출하지
않고 상단 메뉴에서 오버레이로 연다.

### 13.8 Home 모바일 구상

```text
┌──────────────────────┐
│      Omagotchi       │
│ [메뉴 4개 × 2행]     │
├──────────────────────┤
│      01:00:00        │
│      [시작/정지]     │
│                      │
│       [말풍선]       │
│       [캐릭터]       │
├──────────────────────┤
│ Lv.12 캐릭터명       │
│ [경험치──────────]   │
│ [채팅/재실/출석/BGM] │
└──────────────────────┘
```

모바일에서도 캐릭터와 타이머의 상대적인 우선순위를 유지한다. 하단 HUD가 캐릭터를
가리거나 오버레이 위에 남지 않게 한다. 메뉴는 아이콘이 찌그러지지 않는 최소 크기를
보장한다.

### 13.9 Home 영역별 프레임워크 적용

| Home 영역 | 적용 도구 | 적용 내용 |
|---|---|---|
| 상단 메뉴 | React | 메뉴 데이터와 활성 상태 관리 |
| 공통 오버레이 | Radix Dialog | 포커스 이동, ESC 닫기, 배경 비활성화 |
| 진행 화면 탭 | Radix Tabs | 퀘스트·업적·랭킹 전환 |
| 타이머 | React | 시작·정지·복구 상태 표현 |
| 캐릭터 | React + Motion | 상태별 이미지와 짧은 반응 |
| 경험치 | React + Motion | 서버 값 변경 시 증가 애니메이션 |
| 말풍선 | Motion | 머리 위 동일 위치에서 등장·퇴장 |
| 출석·퇴실 확인 | Radix Alert Dialog | 확인과 취소 |
| BGM 음량 | Radix Slider | 키보드와 터치 조작 |
| 도움말 | Radix Accordion | 항목별 열기·닫기 |
| 공간 | React, 필요 시 Phaser | 이동형 공간이 확정됐을 때 Canvas 추가 |

### 13.10 Home 오버레이 공통 구조

모든 오버레이가 똑같이 생길 필요는 없지만 조작 위치는 통일한다.

```text
┌──────────────────────────────────────────────┐
│ 화면 제목                       [닫기]        │
├──────────────────────────────────────────────┤
│ 필요한 경우 탭                                │
├──────────────────────────────────────────────┤
│                                              │
│ 실제 콘텐츠                                  │
│                                              │
├──────────────────────────────────────────────┤
│ 필요한 경우에만 주요 행동 버튼                │
└──────────────────────────────────────────────┘
```

공통 규칙:

- 제목과 닫기 버튼 위치를 고정한다.
- 화면 설명은 꼭 필요할 때만 한 줄 사용한다.
- 탭은 제목 아래 또는 제목과 같은 행 중 하나로 통일한다.
- 빈 상태는 큰 흰 카드가 아니라 콘텐츠 영역 안의 짧은 문장으로 표시한다.
- 모바일에서는 화면 안쪽만 스크롤하고 배경은 움직이지 않게 한다.
- 닫기 버튼, 뒤로 가기, ESC가 같은 결과를 내야 한다.

### 13.11 Index에서 Home으로 이어지는 흐름

```text
Index
  ├── 비로그인 → 로그인 → 초기 캐릭터 설정 → 체크인 → Home
  └── 로그인됨 → 체크인 필요 여부 확인 → Home

Home
  ├── 타이머 시작
  ├── 학습 완료
  ├── 기록 저장
  └── 경험치와 캐릭터 상태 갱신
```

Index의 캐릭터 미리보기와 Home의 실제 캐릭터는 같은 에셋 규격을 사용한다. 다만 Index는
설명용 샘플 상태이고 Home은 서버 또는 실제 사용자 상태를 사용한다.

### 13.12 적용 우선순위

#### Index 우선순위

1. 서비스 설명과 CTA 정리
2. 로그인 상태에 따른 이동 경로 정리
3. 캐릭터 미리보기 추가
4. 모바일 세로 배치 확인
5. 이용 방법 Dialog 또는 Accordion 적용

#### Home 우선순위

1. React 컴포넌트 경계 정리
2. 공통 Dialog와 Tabs 시험 적용
3. 타이머·캐릭터·경험치 상태 연결
4. Motion을 이용한 최소 반응 추가
5. 백엔드 API 연결
6. 공간 요구사항 확정 후 Phaser 검토

### 13.13 적용하지 않을 것

- Index 전체를 게임 Canvas로 제작
- Home 전체를 Phaser로 전환
- 백엔드 연결 전에 가짜 랭킹과 가짜 소속 표시
- 모든 메뉴에 서로 다른 애니메이션 적용
- PC와 모바일을 별도 코드로 중복 구현
- UI 라이브러리의 기본 테마를 그대로 사용

## 14. 외부 코드와 픽셀 에셋 활용 계획

모든 UI를 직접 그리거나 구현할 필요는 없다. 다만 완성된 게임 UI 테마를 통째로 적용하면
오마고치의 정체성이 약해질 수 있으므로 **동작 코드, 픽셀 부품, 공간 에셋을 서로 다른
출처에서 가져와 오마고치 스타일로 다시 조립한다.**

### 14.1 활용 후보

| 출처 | 가져올 대상 | 라이선스·주의사항 | 활용 판단 |
|---|---|---|---|
| Kenney Pixel UI Pack | 버튼, 패널, 진행 바, 슬라이더, 화살표 | CC0 | 우선 검토 |
| NES.css | 픽셀 테두리와 눌림 효과 구현 방식 | MIT | 코드 참고만 |
| itch.io | 실습실 가구, 타일맵, 아이템, 아이콘 | 제작자별로 다름 | 개별 확인 후 사용 |
| OpenGameArt | 스프라이트, 타일, UI, 효과음 | 에셋별로 다름 | 개별 확인 후 사용 |
| Radix UI | Dialog, Tabs, Slider 등의 조작 코드 | 오픈소스, 공식 조건 확인 | 기능 뼈대로 사용 |

### 14.2 Kenney Pixel UI Pack

[Kenney Pixel UI Pack](https://www.kenney.nl/assets/pixel-ui-pack)은 픽셀 패널, 버튼,
슬라이더 등 750개 이상의 파일을 제공하며 CC0로 표시되어 있다.

첫 검토 대상:

1. 패널 프레임 1종
2. 버튼 기본·hover·pressed 상태
3. 경험치 바 프레임
4. 슬라이더
5. 좌우 화살표
6. 체크박스
7. 작은 알림 배지
8. 아이템 슬롯

전체 팩을 화면에 그대로 사용하지 않는다. 필요한 부품만 선택하고 오마고치 색상, 테두리,
크기 규칙에 맞춰 재가공한다.

적용 후보:

| 오마고치 기능 | Kenney 부품 활용 방식 |
|---|---|
| 경험치 | 픽셀 진행 바의 프레임과 채움 영역 |
| 퀘스트 완료 | 작은 배지 또는 도장 바탕 |
| BGM | 슬라이더 손잡이와 트랙 |
| 출석 | 날짜 선택과 도장 상태 |
| 공간 | 아이템 슬롯과 상호작용 표시 |
| 공통 버튼 | 기본·hover·pressed 시각 상태 |

### 14.3 NES.css

[NES.css](https://www.npmjs.com/package/nes.css)는 MIT 라이선스의 8비트 스타일 CSS
프레임워크다.

전체 스타일시트를 서비스에 바로 적용하지 않는다. 다음 구현 방식만 참고한다.

- 픽셀 테두리를 CSS로 만드는 방식
- 버튼의 눌린 상태와 그림자
- 말풍선 꼬리
- 진행 바 형태
- 체크박스와 라디오 표현

NES.css 클래스를 화면 곳곳에서 직접 사용하는 대신 참고한 패턴을 공통 컴포넌트 CSS에
다시 구현한다.

```text
NES.css 참고
    ↓
Omagotchi 디자인 토큰 적용
    ↓
GameButton / GamePanel / CharacterBubble
```

이렇게 해야 외부 프레임워크를 제거하거나 변경할 때 서비스 전체가 영향을 받지 않는다.

### 14.4 itch.io

[itch.io 상업 이용 가능 에셋](https://itch.io/game-assets/tag-commercial-use)에서는 다음
자료를 찾을 수 있다.

- 실습실 책상과 의자
- 컴퓨터, 사물함, 화이트보드
- 책, 연필, 타이머 아이템
- 출석 도장
- 공간 화면용 바닥과 벽 타일
- 퀘스트·업적 아이콘
- 캐릭터 주변 소품

`commercial-use` 태그가 있어도 실제 이용 조건은 제작자마다 다를 수 있다. 다운로드 전에
상업 사용, 수정, 출처 표시, 재배포 금지 여부를 상품 페이지에서 확인한다.

유료 팩은 구매 계정과 영수증도 팀이 확인할 수 있는 위치에 보관한다.

### 14.5 OpenGameArt

[OpenGameArt](https://opengameart.org/)에서는 픽셀 스프라이트, 타일, 효과음 등을 찾을
수 있다. CC0뿐 아니라 CC-BY, CC-BY-SA 등 여러 라이선스가 섞여 있으므로 에셋마다
조건을 따로 기록한다.

OpenGameArt는 우선 다음 용도로 검토한다.

- 공간 기능 프로토타입용 임시 타일
- 학습 완료 효과
- 레벨업 효과음
- 테스트용 NPC와 배경 소품

서비스의 대표 캐릭터와 로고는 외부 에셋으로 대체하지 않는다.

### 14.6 외부 요소의 조합 방식

```text
Radix UI
└── Dialog·Tabs·Slider의 실제 조작과 접근성

Kenney Pixel UI
└── 버튼·패널·진행 바의 픽셀 부품

NES.css
└── 픽셀 CSS 구현 방식 참고

itch.io / OpenGameArt
└── 공간 소품·타일·효과음 후보

기존 오마고치 에셋
└── 캐릭터·나뭇가지·말풍선·로고·대표 아이콘
```

외부 에셋은 화면의 재료로만 사용한다. 최종 색상, 간격, 크기, 텍스트, 상호작용 규칙은
오마고치 디자인 시스템에서 결정한다.

### 14.7 코드 컴포넌트 적용 예시

```jsx
<GameDialog open={open} onOpenChange={setOpen}>
  <GameTabs value={tab} onValueChange={setTab}>
    <QuestList />
    <AchievementList />
    <RankingList />
  </GameTabs>
</GameDialog>
```

- `GameDialog`의 포커스와 닫기 동작은 Radix를 사용한다.
- 패널 프레임은 Kenney 부품 또는 이를 참고한 CSS를 사용한다.
- 눌린 버튼 표현은 NES.css 구현 방식을 참고한다.
- 색상과 캐릭터 표현은 오마고치 고유 디자인을 사용한다.

외부 출처가 각 기능 컴포넌트에 직접 퍼지지 않게 `GameButton`, `GamePanel`,
`GameDialog`, `ProgressBar` 같은 공통 컴포넌트 안에 감싼다.

### 14.8 에셋 저장 구조

```text
src/main/resources/static/assets/
├── omagotchi/
│   ├── characters/
│   ├── logo/
│   └── ui/
└── vendor/
    ├── kenney-pixel-ui/
    │   ├── images/
    │   ├── LICENSE.txt
    │   └── SOURCE.md
    └── creator-pack-name/
        ├── images/
        ├── LICENSE.txt
        └── SOURCE.md
```

원본과 수정본을 구분해야 할 경우 `original/`, `modified/` 폴더를 둔다. 외부 파일의
이름을 전부 바꾸기 전에 원본 파일명과 출처를 기록한다.

### 14.9 라이선스 문서

저장소 루트 또는 `docs`에 `ASSET_LICENSES.md`를 작성하고 다음 항목을 기록한다.

```text
- 에셋 이름
- 제작자
- 원본 주소
- 다운로드 날짜
- 라이선스
- 출처 표시 필요 여부
- 수정 여부
- 사용 화면
- 구매 증빙 위치 — 유료인 경우
```

CC-BY 에셋은 서비스의 크레딧 화면에도 제작자와 링크를 표시한다. 라이선스가 명확하지
않은 무료 에셋은 사용하지 않는다.

### 14.10 첫 시험 적용 범위

외부 에셋 도입 시험은 다음 네 컴포넌트로 제한한다.

```text
GameButton
GamePanel
GameDialog
ProgressBar
```

시험 순서:

1. Kenney 팩에서 후보 부품을 고른다.
2. 오마고치 초록 팔레트로 시험 재가공한다.
3. Radix 동작 위에 픽셀 외형을 적용한다.
4. Storybook에서 기본·hover·pressed·disabled 상태를 비교한다.
5. 현재 UI보다 오마고치 정체성이 좋아졌는지 검토한다.
6. 코드와 CSS가 줄어들지 않으면 도입을 중단한다.

### 14.11 가져오지 않을 것

- 완성된 게임 UI 테마 전체
- 다른 게임의 캐릭터와 로고
- 라이선스가 표시되지 않은 무료 이미지
- Octodoro와 비슷한 색·탭·보상 체계가 묶인 템플릿
- Unity·Unreal 전용 파일처럼 웹에서 바로 관리하기 어려운 에셋
- 같은 역할의 아이콘 팩 여러 종류
- 외부 CSS 프레임워크의 전역 스타일 전체

---

## 15. 최종 제안

주말 검토 후 첫 작업은 아래 정도로 제한한다.

```text
1. Storybook 설치
2. 디자인 토큰 작성
3. GameButton·GameDialog·GameTabs 제작
4. Radix Dialog와 Tabs 시험 적용
5. Motion으로 오버레이와 경험치 반응만 적용
```

Phaser, XState, Rive, 모바일 앱 패키징은 이 단계에 포함하지 않는다.
먼저 공통 UI가 실제로 단순해지고 유지보수가 쉬워지는지 확인한 뒤 다음 도구를 결정한다.

현재 코드 기준의 설치 명령, 선행 작업과 검증 기준은
[React 게임 UI 도입 실행 체크리스트](react-ui-adoption-checklist.md)를 따른다.
