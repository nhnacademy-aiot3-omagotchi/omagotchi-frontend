# Home UI React Island 리팩토링 기록

## 목적

이번 작업은 모바일 전용 애플리케이션을 새로 만드는 작업이 아니라, 기존 Home 화면을 화면 비율 변화에 더 잘 대응하는 웹앱형 UI 구조로 정리하기 위한 1차 리팩토링이다.

기존 Home 화면은 데스크톱 기준에서는 크게 문제 없어 보였지만, 브라우저 폭과 높이가 조금만 바뀌어도 상단 메뉴, 타이머, 캐릭터, 하단 HUD, 도크 버튼이 서로 다른 기준으로 움직이며 어색하게 깨졌다. 이 문제는 특정 모바일 기기 몇 개를 기준으로 CSS를 추가한다고 해결되는 문제가 아니다.

따라서 Home 화면을 기기별 페이지가 아니라 하나의 유동적인 Home stage로 보고, UI 단위를 컴포넌트로 분리하는 방향을 선택했다.

## 왜 리팩토링이 필요했는가

Home 화면은 단순히 요소를 예쁘게 배치하는 화면이 아니다. 실제 서비스에서는 타이머, 출석, 퇴실, 캐릭터 성장, 경험치, 채팅, 재실 인원, 메뉴 오버레이가 한 화면 안에서 동시에 움직인다. 기존 구조는 이 요소들이 각자 다른 CSS 기준점에 고정되어 있어서 화면 비율이 조금만 바뀌어도 서로 겹치거나, 일부 버튼이 화면 밖으로 밀리거나, 닉네임과 레벨이 뒤섞이는 문제가 반복됐다.

특히 문제가 컸던 영역:

- 하단 HUD: 닉네임, 레벨, 경험치 바, 채팅 입력, BGM, 출석부, 재실 인원, 퇴실 버튼이 같은 하단 영역을 공유했다.
- 모바일 세로 화면: 채팅 입력이 카드처럼 커지고 레벨/닉네임/XP와 순서가 어색해졌다.
- 모바일 가로 화면: 캐릭터, XP, 채팅, 도크 버튼이 한 줄에 몰려 서로 침범했다.
- 오버레이: 상단 제목과 탭 네비게이션이 겹치고, 내부 폰트가 Home의 게임 UI 톤과 어울리지 않았다.
- viewport 기준: 특정 수치에 맞춰 보정하면 다른 화면 크기에서 다시 깨졌다.

그래서 리팩토링의 목표는 "모바일 화면을 따로 하나 더 만드는 것"이 아니라, Home 자체를 화면 비율 변화에 견디는 구조로 바꾸는 것이다.

## 현재 결정

- Home의 최종 진입점은 `/home`으로 유지한다.
- `/home`을 모바일 화면이라고 해서 별도 Home 경로로 자동 이동시키지 않는다.
- 인증, 인가, JWT, 세션, 로그인 성공 흐름은 변경하지 않는다.
- 이번 작업은 프론트 표현 계층 작업으로 한정한다.
- 기존 기능 로직은 가능한 그대로 사용한다.
- React는 전체 서비스 전환이 아니라 Home UI 영역에만 island 형태로 적용한다.

## 왜 React Island인가

Home 화면은 단순 정적 페이지가 아니라 여러 상태가 한 화면 안에서 동시에 움직이는 구조다.

- 타이머 상태
- 캐릭터 상태
- 레벨과 경험치 상태
- 출석 상태
- BGM 패널 상태
- 재실 인원 패널 상태
- 오버레이 열림 상태
- 채팅/HUD 표시 상태
- 화면 비율에 따른 배치 상태

기존 Vanilla JS 방식은 `querySelector`로 DOM을 찾고 직접 값을 바꾸는 방식이라, 화면이 커질수록 UI 구조와 상태 흐름을 따라가기 어려워진다. React island는 Home UI를 컴포넌트 단위로 나누되, 기존 기능 로직을 한 번에 갈아엎지 않기 위한 중간 단계다.

## 이번 작업 범위

이번 리팩토링에서 React가 맡는 것은 UI 구조 렌더링이다.

React로 분리한 영역:

- 상단 로고와 메뉴
- BGM 패널 껍데기
- 재실 인원 HUD 껍데기
- 타이머 패널
- 캐릭터 표시 영역
- 레벨과 경험치 HUD
- 채팅 바
- 하단 도크 버튼

오버레이는 아직 기존 `home.js`의 문자열 템플릿과 이벤트 위임 구조를 유지한다. 다만 UI 방향은 Home React island와 맞춘다.
즉, 다음 단계에서 도움말, 진행, 내 정보, 기수, 학습 기록, 공간, 커뮤니티, 설정 오버레이를 기능 단위 React 컴포넌트로 옮기되, Backend API 호출은 컴포넌트 안에 직접 흩뿌리지 않고 공통 API/helper 계층으로 분리한다.

## 이번 리팩토링에서 바로 정리한 것

### 1. 하단 HUD 순서

모바일과 좁은 화면에서는 하단 정보를 다음 순서로 본다.

```text
채팅 입력
닉네임 / 레벨
경험치 바
도크 버튼
```

이 순서를 택한 이유는 사용자가 메시지를 입력할 때 하단 버튼과 겹치지 않아야 하고, 닉네임과 레벨은 경험치 바의 설명 역할을 해야 하기 때문이다. 레벨과 닉네임은 같은 줄 안에서 서로 밀어내지 않고, 레벨은 왼쪽 기준, 닉네임은 중앙 기준으로 배치한다.

### 2. 도크 버튼 그룹화

BGM, 출석부, 재실 인원, 퇴실 버튼은 모두 빠른 실행 버튼이다. 따라서 모바일에서는 각 버튼을 따로 고정하지 않고 `home-action-dock` 안에서 하나의 도크 그룹으로 다룬다.

퇴실 버튼은 기존 출석 상태 로직을 그대로 따른다. 출석 전에는 숨겨지고, 출석 후에만 표시된다. 표시 여부에 따라 도크 폭이 달라질 수 있으므로 CSS에서 하단 안전 영역을 다시 계산한다.

### 3. 채팅 바 정리

채팅 바는 PC에서는 기존처럼 GLOBAL/COHORT 탭과 입력칸을 함께 보여준다. 모바일에서도 기능이 갑자기 사라지지 않도록 탭은 유지하되, 입력 영역을 작게 줄이고 하단 정보보다 위에 배치한다.

### 4. 오버레이 UI 정리

오버레이는 아직 React 컴포넌트로 완전히 이관하지 않았다. 대신 기존 기능을 깨지 않는 선에서 다음을 먼저 정리했다.

- 오버레이 배경을 어둡게 깔고 blur를 적용해 Home stage와 분리한다.
- PC에서는 중앙 패널, 모바일에서는 하단에 가까운 패널처럼 보이게 한다.
- 오버레이 제목 영역과 내부 탭 네비게이션이 겹치지 않도록 sticky 기준을 조정한다.
- 탭 폰트는 본문 UI에 맞는 시스템 폰트로 바꿔 과한 게임 폰트 사용을 줄인다.
- 카드, 목록, 입력, 버튼의 radius와 그림자를 통일한다.

기존 JavaScript가 계속 맡는 영역:

- 타이머 동작
- 캐릭터 이미지와 반응 처리
- 경험치와 레벨 계산
- 출석 처리
- BGM 제어
- 재실 인원 패널 제어
- 홈 오버레이 열기/닫기
- 학습 기록, 공간, 커뮤니티 등 기존 화면 로직

즉, 이번 작업은 기능을 React로 전부 다시 작성한 것이 아니라 기존 기능이 기대하는 DOM 구조를 React가 렌더링하도록 옮긴 1차 마이그레이션이다.

## 유지한 원칙

기존 `home.js`가 사용하는 `data-*` 연결 지점은 유지했다. 이 덕분에 React 도입 후에도 기존 타이머, 캐릭터, 출석, BGM, 재실 인원, 오버레이 로직이 같은 방식으로 DOM을 찾을 수 있다.

React 번들은 기존 `home.js`보다 먼저 로드된다. 기존 `home.js`가 초기 실행 시점에 DOM을 바로 조회하기 때문에, React가 먼저 Home UI DOM을 만들어두는 순서가 필요하다.

리팩토링 중에도 다음은 건드리지 않는다.

- 인증, 인가, JWT, 세션 처리
- 로그인 성공 후 서버 redirect 정책
- 기존 BFF/API 호출 경계
- `home.js`가 기대하는 `data-*` 속성
- 출석 상태에 따른 퇴실 버튼 표시 조건

## 빌드 방식

Home React island는 Vite로 빌드한다.

- 개발 중에는 Home React 소스를 수정한 뒤 Home 번들을 다시 빌드한다.
- 빌드 결과물은 Spring 정적 리소스 경로에 생성된다.
- Spring MVC와 Thymeleaf 서버 구조는 그대로 유지한다.

## 레이아웃 방향

앞으로 Home 화면은 특정 기기 크기를 따라가는 방식으로 만들지 않는다.

좋지 않은 방향:

- 특정 iPhone 크기만 보고 CSS 작성
- 특정 Android 크기만 보고 CSS 작성
- DevTools에서 보이는 특정 폭 하나에 맞춰 위치 고정
- 화면이 깨질 때마다 새 breakpoint 추가

지향하는 방향:

- 화면 비율 기준으로 배치 모드 결정
- 사용 가능한 폭과 높이를 기준으로 요소 크기 조절
- 최소값, 선호값, 최대값을 가진 유동 크기 사용
- 세로형, 가로형, 낮은 높이 화면을 별도 레이아웃 상태로 처리
- Home 전체를 하나의 웹앱 stage처럼 관리


## 다음 단계

1. React Home UI가 기존 기능과 충돌 없이 동작하는지 확인한다.
2. 데스크톱, 좁은 화면, 가로 화면에서 Home stage 배치가 무너지지 않는지 본다.
3. 기존 `home.js` 중 UI 상태와 강하게 묶인 부분을 작은 단위로 React 상태로 옮길지 검토한다.
4. 오버레이 UI는 `data-home-overlay` 진입 계약을 유지한 채 React 컴포넌트로 점진 이관한다.
5. 폐기한 모바일 전용 경로와 viewport redirect 시도가 반복되지 않도록
   [Home UI 전환 검토 기록](home-ui-decision-history.md)을 기준으로 리뷰한다.
