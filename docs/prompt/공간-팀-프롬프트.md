# Space / Team Frontend Backend Integration Prompt

## Purpose

현재 프론트엔드의 Space 화면, Team 관련 화면, 그리고 관리자 대시보드의 공간/팀 관련 영역을 백엔드 API와 연결하는 작업이다.

핵심 목표는 기존 화면 흐름과 관리자 대시보드 틀을 깨지 않고, Mock 데이터를 Backend Response로 치환하는 것이다.

## Frontend Ownership Map

Space / Team 담당자는 아래 파일 범위 안에서 작업한다.

### Space User Page

HTML:

- `src/main/resources/templates/pages/app/space.html`
- `src/main/resources/templates/pages/app/home.html`, 홈의 공간 진입 CTA 또는 공간 오버레이 연결이 필요한 경우만

CSS:

- `src/main/resources/static/css/space.css`
- `src/main/resources/static/css/spaceRoom.css`
- `src/main/resources/static/css/home.css`, 홈 오버레이 또는 공간 CTA 표시가 필요한 경우만

JS:

- `src/main/resources/static/js/space.js`
- `src/main/resources/static/js/spaceRoom.js`
- `src/main/resources/static/js/home.js`, 홈 오버레이 mount 연결이 필요한 경우만
- `src/main/resources/static/js/api.js`, Space API helper 추가가 필요한 경우만

Controller:

- `src/main/java/site/omagotchi/frontend/presentation/MainPageController.java`

주의:

- `/space` URL은 유지한다.
- `space.html`의 `data-space-room-app` mount point는 유지한다.
- `spaceRoom.js`가 렌더링하는 내부 UI는 유지하되, 데이터 공급원을 Mock에서 Backend Response로 교체한다.
- Controller는 view name 연결만 담당한다. API proxy, 권한 판단, 비즈니스 로직을 Controller에 넣지 않는다.

### Team User Area

HTML 후보:

- `src/main/resources/templates/pages/app/cohort.html`
- `src/main/resources/templates/pages/app/space.html`
- `src/main/resources/templates/pages/app/progress.html`, 팀 랭킹 표시가 Backend 명세에 있는 경우만

CSS 후보:

- `src/main/resources/static/css/appPages.css`
- `src/main/resources/static/css/space.css`
- `src/main/resources/static/css/progress.css`, 팀 랭킹 표시가 Backend 명세에 있는 경우만

JS 후보:

- `src/main/resources/static/js/space.js`
- `src/main/resources/static/js/spaceRoom.js`
- `src/main/resources/static/js/progress.js`, 팀 랭킹 표시가 Backend 명세에 있는 경우만
- `src/main/resources/static/js/api.js`, Team API helper 추가가 필요한 경우만

Controller 후보:

- `src/main/java/site/omagotchi/frontend/presentation/HomeMenuController.java`
- `src/main/java/site/omagotchi/frontend/presentation/MainPageController.java`

신규 파일이 필요한 경우:

- Team 전용 JS가 커지면 `src/main/resources/static/js/team.js`를 추가할 수 있다.
- Team 전용 화면이 Backend/API 명세와 라우팅 요구에 포함된 경우에만 `templates/pages/app/team.html`과 Controller route를 추가한다.
- 신규 route 추가 전에는 기존 URL을 바꾸지 말고, 추가 route가 필요한 이유를 작업 결과에 적는다.

### Manager Dashboard Space / Team Area

HTML:

- `src/main/resources/templates/pages/manager/managerDashboard.html`

CSS:

- `src/main/resources/static/css/managerDashboard.css`

JS:

- `src/main/resources/static/js/managerDashboard.js`
- `src/main/resources/static/js/api.js`, manager dashboard API helper 추가가 필요한 경우만

Controller:

- `src/main/java/site/omagotchi/frontend/presentation/ManagerPageController.java`

주의:

- 관리자 대시보드의 `sensors`, `members`, `attendance`, `overview` 패널 안에서 필요한 데이터만 연결한다.
- 기존 `data-dashboard-panel`, `data-dashboard-tab`, `data-cohort-select` 셀렉터는 변경하지 않는다.
- 관리자 화면에서 Space/Team 때문에 새 레이아웃을 만들지 않는다.

### Out Of Scope

아래 파일은 Space / Team 담당자가 임의 수정하지 않는다.

- 인증 화면: `templates/pages/auth/*`
- 회원가입/로그인 JS: `static/js/login.js`, `static/js/register.js`, `static/js/username.js`
- 캐릭터 선택 화면: `templates/pages/onboarding/characterSelector.html`
- 에러 화면: `templates/error/*`
- 공통 레이아웃: `templates/layouts/managerLayout.html`, 단 관리자 레이아웃 자체 변경 요구가 명시된 경우는 예외
- 출석 전용 로직: `static/js/attendanceState.js`, `static/js/home/attendance.js`, 단 Space 상태와 명세상 연결된 경우는 예외

## Common Rules

### Scope

- 현재 존재하는 화면, 라우팅, HTML 구조, CSS 클래스, `data-*` 셀렉터를 기준으로 API를 연결할 것.
- 화면 흐름을 임의로 변경하지 말 것.
- 관리자 대시보드는 기존 레이아웃, 탭 구조, 카드/테이블 배치를 유지할 것.
- 기존 UX에서 필요한 데이터만 Backend Response에 맞춰 치환할 것.
- Backend API 명세에 없는 기능은 구현하지 말 것.
- API 응답 필드명이 기존 프론트 상태명과 다르면 프론트 내부에 매핑 레이어를 둘 것.

### Data Handling

- 새로운 Mock 데이터 생성 금지.
- 기존 Mock 데이터는 제거하거나 API 실패 시 fallback 용도로만 분리할 것.
- 목록, 상세, 생성, 수정, 삭제의 성공/실패 상태는 Backend Response 기준으로 처리할 것.
- null, 빈 배열, 빈 문자열, 권한 없음, 삭제된 리소스 상태를 반드시 UI에서 처리할 것.
- 프론트에서 임의로 소유자, 권한, 상태값을 추론하지 말 것.

### Authorization

- 기본적으로 기존 `src/main/resources/static/js/api.js`의 `window.OmagotchiApi` helper를 사용한다.
- 현재 프론트는 `/bff/v1` same-origin 호출을 기준으로 하므로, 화면 JS에서 access token을 직접 꺼내 붙이지 않는다.
- Backend를 직접 호출해야 하는 명세가 별도로 주어진 경우에만 REST API 요청에 `Authorization: Bearer {accessToken}`을 사용한다.
- 권한 판단은 Backend가 JWT와 Membership 기준으로 수행한다.
- Frontend는 버튼 노출, 비활성화, 안내 메시지 같은 UX 처리만 담당한다.

금지:

- `userId` 직접 전달
- `cohortId` 직접 전달, 단 Backend API 명세에서 명시적으로 요구한 route/query parameter는 예외
- `memberId` 직접 전달, 단 관리자 API에서 명시적으로 대상 식별자로 요구한 경우는 예외
- `role`, `admin`, `isManager` flag 전달
- 클라이언트에서 권한 우회
- Backend에 없는 데이터 임의 생성

## Space Area

### Target

- 사용자 Space 화면
- 홈 화면의 공간 오버레이 또는 공간 진입 CTA
- 실습실, 회의실, 도서관 등 공간 상태 표시
- 공간 사용 신청, 입장, 퇴장, 예약, 초대 등 현재 화면에 이미 존재하는 액션

### Implementation Rules

- 기존 Space UI의 화면 흐름을 유지한다.
- 현재 화면에 없는 신규 공간 기능을 추가하지 않는다.
- 공간 상태, 현재 인원, 사용 가능 여부, 센서 값, 예약 가능 시간은 Backend Response를 그대로 표시한다.
- Frontend에서 공간 점유 상태, 사용 가능 여부, 참가 가능 여부를 계산하지 않는다.
- 빈 공간, 만석, 권한 없음, 이미 참여 중, 삭제된 공간, 비활성 공간 상태를 UI에서 구분해 표시한다.
- Space 화면의 기존 JS mount point와 `data-space-room-app` 구조를 유지한다.

### Do Not

- 전체 공간 목록을 받은 뒤 프론트에서 임의 필터링하여 권한 범위를 만들지 말 것.
- 프론트에서 공간 정원 초과 여부를 최종 판단하지 말 것.
- 프론트에서 임시 room id, 임시 participant id, 임시 invitation id를 만들지 말 것.
- Storage URL, 이미지 경로, 센서 상태를 임의 생성하지 말 것.

## Team Area

### Target

- Team 관련 사용자 화면
- 팀 목록, 팀 상세, 팀원 표시, 팀 참여/탈퇴/초대/관리 액션
- 팀 기준 랭킹 또는 공간과 연결된 팀 표시가 있다면 Backend Response 기반으로 연결

### Implementation Rules

- Team 화면이 아직 명확히 분리되어 있지 않다면 기존 화면 내부의 관련 영역만 연결한다.
- 신규 라우트나 신규 화면은 Backend API 명세와 현재 프론트 라우팅에 명시된 경우에만 추가한다.
- 팀 생성, 수정, 삭제, 참여, 탈퇴, 초대, 승인 액션은 Backend Response 기준으로 처리한다.
- 팀원 권한, 팀장 여부, 관리자 여부는 Backend가 내려준 action availability 또는 permission response를 기준으로 UI 처리한다.
- 팀원 목록 정렬, 팀 랭킹, 점수 계산은 Backend 결과를 그대로 표시한다.

### Do Not

- Frontend에서 팀장 여부를 `userId === leaderId` 방식으로 판단하지 말 것.
- Frontend에서 팀 순위, 점수, 활동 시간을 직접 계산하지 말 것.
- Backend에 없는 팀 상태값을 만들지 말 것.
- 팀 초대, 승인, 탈퇴 성공을 optimistic update로 확정하지 말 것.

## Manager Dashboard Constraints

관리자 대시보드는 기존 틀 안에서만 API를 연결한다.

유지할 것:

- 기존 관리자 레이아웃
- 사이드바 탭 구조
- 대시보드 패널 구조
- 카드, 테이블, 폼, 모달의 배치
- 기존 CSS 클래스와 `data-dashboard-*` 셀렉터

허용:

- Mock 데이터 제거
- API service 함수 추가
- Backend Response를 화면 상태로 매핑
- Loading, Empty, Error 상태 표시
- 서버 validation 메시지 표시

금지:

- 관리자 대시보드 전체 레이아웃 재작성
- Bootstrap 또는 다른 UI 프레임워크 신규 도입
- 탭 이름, URL, 주요 화면 흐름 변경
- 관리자 권한을 Frontend에서 계산
- 관리자용 `role/admin flag`를 request body에 넣기

## API Layer Convention

- API 호출 코드는 한 곳에서 관리한다.
- 화면 컴포넌트나 페이지 스크립트 안에 `fetch`를 직접 흩뿌리지 않는다.
- 기존 `src/main/resources/static/js/api.js`의 `window.OmagotchiApi` 패턴을 우선 사용한다.
- Space API와 Team API는 service 단위로 분리한다.
- 요청/응답 매핑 함수는 UI 렌더링 코드와 분리한다.

권장 구조:

```text
static/js/api.js
static/js/space.js
static/js/spaceRoom.js
static/js/team.js
static/js/managerDashboard.js
```

단, 실제 파일 추가 여부는 현재 프로젝트 구조와 Backend API 명세를 보고 결정한다.

## Required States

모든 API 연결 화면은 다음 상태를 처리한다.

- Loading
- Empty
- Error
- Unauthorized
- Forbidden
- Not Found
- Success
- Validation Error

- 연결한 API 목록

- 추가한 service/helper 목록
- Backend Response와 Frontend state 매핑표
- 필요한 Backend field
- 오류가 발생한 API와 재현 방법
- 관리자 대시보드에서 변경한 패널 목록
- `userId`, `role`, `admin flag`를 직접 전달하지 않았는지 확인
- `./mvnw test` 또는 해당 프로젝트의 검증 명령 실행 결과
