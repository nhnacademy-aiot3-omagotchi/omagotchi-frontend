## 1. 목적과 현재 상태

기존 Space·Party UI와 화면 흐름을 유지하면서 확정된 Backend API를 View BFF를 통해
연결한다. UI 재설계, 인증 구조 변경, 공통 컴포넌트 리팩터링은 이 작업 범위가 아니다.

- 기준일: 2026-08-29
- Frontend 상태: 화면과 브라우저 내부 Prototype 동작 완료
- Backend 상태: Space·Party·Occupancy 계약 및 API 연결 대기
- 기존 Backend Handoff 범위: `space`, `team`, `occupancy` 제외
- Browser API 경계: Same-Origin `/bff/v1/**`
- 인증 경계: HttpOnly Session Cookie, Browser에 JWT 원문 노출 금지

현재 입장·반납·연장·공실 알림·도서관·파티 동작은 실제 서버 상태가 아니다.
`spaceRoom.js`의 메모리와 `sessionStorage`를 변경하는 Prototype이므로 다른 사용자와
공유되지 않고 동시성·권한·영속성을 보장하지 않는다.

문서에서 `Party`는 현재 UI가 사용하는 용어다. Backend가 `Team`이라는 Domain 명칭을
사용한다면 확정된 DTO와 Endpoint를 확인한 뒤 mapping 계층에서만 이름 차이를 흡수한다.

## 3. 실제 Runtime 구조

```text
/home
  → homeBootstrap.js가 Profile 조회
  → spaceRoom.js 로드
  → home.js 로드
  → 공간 메뉴 클릭
  → home.js가 [data-space-room-app] 생성
  → OmagotchiSpaceRoom.mount(...)

/space
  → pages/app/space.html
  → spaceRoom.js
  → space.js
  → OmagotchiSpaceRoom.mount(...)
```

Storybook의 `HomeMenuPanel.jsx`는 UI 시안과 상태 검증용이다. 실제 Home은 `home.js`가 만든
내부 Template을 React `HomeOverlay`와 `HomeMenuLiveContent`가 감싸고, `spaceRoom.js`가
`[data-space-room-app]`에 기능 UI를 Mount한다.

Backend 연결 시 Storybook fixture나 `defaultRooms`, `defaultParty`를 실제 Runtime으로
가져오지 않는다.

## 4. 현재 Prototype의 Source of Truth

현재 `spaceRoom.js`의 다음 값은 Browser 로컬 상태다.

```text
state.rooms
state.party
state.alertRoomIds
state.libraryInside
state.selectedRoomId
state.roomPage
```

- 초기 `rooms`는 빈 배열이다.
- Production 코드에는 사용자용 회의실 목록 API 호출이 없다.
- `OmagotchiSpaceRoom.updateData(...)`와 `omagotchi:space-data` Event로 데이터를 주입할 수
  있지만 Backend adapter는 연결돼 있지 않다.
- 입장·반납·연장·알림·도서관·파티 작업은 객체를 직접 수정한 뒤 `sessionStorage`에
  저장한다.
- 같은 Tab의 새로고침에서는 복원될 수 있지만 다른 Session·사용자·기기에는 전달되지
  않는다.
- Browser 시계가 점유 만료를 판정하고 있어 실제 서비스의 정본으로 사용할 수 없다.
- `/bff/v1/admin/sensors/spaces`는 관리자 Sensor 공간 메타데이터용이다. 사용자 회의실
  점유·파티 API로 재사용하지 않는다.

## 6. 연결 전 확정해야 할 Backend 계약

아래 Domain·BFF Endpoint, Method, Request·Response DTO, 오류 Status와 권한 정책이
확정되기 전에는 경로와 Field를 추측하지 않는다.

| 기능 | 필요한 계약 | 현재 상태 |
| --- | --- | --- |
| 회의실 | 목록·상세 조회 | 미확정 |
| 회의실 점유 | 입장·반납·연장 | 미확정 |
| 참여자 | 추가·제외·내 참여 종료 | 미확정 |
| 공실 알림 | 신청·취소·내 신청 목록 | 미확정 |

| 파티원 | 사용자 검색·초대·수락·거절·제외 | 미확정 |

계약에는 최소한 다음 정책이 포함되어야 한다.

- 현재 사용자와 소속 기수 식별 방법

- 한 사용자당 동시 점유·참여 가능 수
- 점유 생성·연장·반납의 소유자 및 참여자 권한
- 동시 입장 충돌 처리와 `409 Conflict` 등 오류 Code
- 파티 최대 인원, Master 권한, 초대·수락 정책
- 공실 알림 신청 대상, 중복 신청, Telegram 미연동 처리
- 도서관 상태가 Presence·출석과 연동되는지 여부
- Sensor 공간 ID와 회의실 ID의 관계
- 목록·상세 Polling 주기, 숨은 Tab 중지 여부와 실패 시 Backoff 정책

## 7. 현재 UI의 Mapping 대상

아래 JSON은 확정 API DTO가 아니라 현재 UI State가 사용하는 최소 형태다. Backend DTO를
이 모양으로 강제하지 않고 `spaceRoom.js`의 순수 mapping 함수에서 변환한다.

```json
{
  "rooms": [
    {
      "id": "room-id",
      "name": "회의실",
      "status": "AVAILABLE",
      "capacity": 8,
      "inactiveReason": null,
      "sensor": {
        "co2": 700,
        "temperature": 24,
        "humidity": 45
      },
      "occupancy": null
    }
  ],
  "party": null,
  "cohortMembers": [],
  "telegram": {
    "connected": false,
    "connectPath": "/bff/v1/me/telegram/connect/opaque-handle"
  }
}
```

점유 중인 경우 현재 UI는 아래 정보가 필요하다.

```json
{
  "ownerId": "user-id",
  "cohortId": "cohort-id",
  "cohortName": "기수 이름",
  "startedAt": 0,
  "expiresAt": 0,
  "extensionCount": 0,
  "participants": [
    { "id": "user-id", "name": "표시 이름" }
  ]
}
```

- ISO-8601 시간은 mapping 단계에서 현재 UI가 사용하는 Epoch millisecond로 변환하거나,
  렌더링 함수를 ISO-8601 기준으로 통일한다.
- Browser 시계로 만료를 확정하지 않는다. Backend 판정과 응답을 Source of Truth로 쓴다.
- 소유권·기수·권한을 ID 비교만으로 확정하지 않는다. Backend의 권한 결과 또는 허용 Action
  Field를 따른다.
- Character 이미지 경로는 기존 Frontend Asset mapping을 사용하고, Backend URL을 임의로
  신뢰하지 않는다.

11. BFF Polling은 같은 mapping과 Render 경계를 재사용하고, 화면이 열려 있을 때만
    동작하도록 연결한다.

한 변경에서 모든 기능을 동시에 연결하지 않는다. 권장 순서는 다음과 같다.

```text
조회
  → 회의실 점유
  → 참여자
  → 파티
  → 공실 알림
  → 도서관
  → BFF Polling 동기화
```

### BFF Polling 원칙

- WebSocket과 STOMP를 추가하지 않는다.
- Browser는 `window.OmagotchiApi`를 통해 Same-Origin `/bff/v1/**`만 주기적으로 조회한다.
- 공간 Overlay 또는 `/space` Page가 보일 때만 Polling한다.
- `document.visibilityState !== "visible"`이면 Polling을 중지하고, 다시 보일 때 즉시 한 번
  조회한 뒤 재개한다.
- 이전 요청이 끝나기 전에 다음 요청을 중복 실행하지 않는다.
- Network·`5xx` 실패가 반복되면 고정 간격으로 호출을 계속하지 말고 Backoff한다.
- 입장·반납·연장 같은 명령은 Polling 결과를 기다려 성공으로 판단하지 않는다. 명령 API의
  성공 응답으로 즉시 갱신하고, 이후 Polling으로 다른 사용자 변경을 동기화한다.
- 동시 입장·정원·권한 판정은 Polling이 아니라 Backend 명령 처리에서 원자적으로 보장한다.
- Polling 주기와 응답 Payload 범위는 Backend 담당자와 합의하고 코드에 근거 없이 임의로
  정하지 않는다.

## 11. Action 연결 원칙

| 현재 Prototype Action | Backend 연결 후 원칙 |
| --- | --- |
| 회의실 입장 | Server가 출석·중복 참여·정원·점유 충돌을 검증한 뒤 성공 응답으로 갱신 |
| 반납 | 현재 사용자가 Owner인지 Server가 검증 |
| 연장 | 연장 가능 시간·횟수를 Server가 판정 |
| 참여 종료 | 본인 참여 정보는 Session 사용자 기준으로 처리 |
| 참여자 추가·제외 | 권한과 대상 사용자를 Server가 검증 |
| 공실 알림 신청·취소 | Server 저장 후 내 신청 상태를 응답으로 갱신 |
| 도서관 입·퇴장 | Presence·출석 연동 정책에 따라 Server 상태 갱신 |
| 파티 생성·수정·해체 | 현재 사용자와 Master 권한을 Server가 판정 |
| 파티원 초대·제외 | 검색 권한, 기수 범위, 중복·정원을 Server가 검증 |

- 현재 사용자 ID, 기수 ID, role, admin flag를 권한 증명으로 Request Body에 보내지 않는다.
- 대상 사용자나 Resource ID가 필요한 Action은 확정 API 계약에 정의된 Field만 사용한다.
- 전체 Space·Party 데이터를 받은 뒤 Frontend에서 권한 범위를 필터링하지 않는다.
- Backend가 제공하지 않은 성공·예약·초대·점유 상태를 Frontend에서 생성하지 않는다.

## 12. 인증과 Telegram 보안

### 공통 인증

```text
Browser
  → Same-Origin Session Cookie
  → Frontend /bff/v1/**
  → Session의 Access Token을 Domain Service에 Bearer relay
```

- Access Token과 Refresh Token을 HTML, JavaScript, URL, `localStorage`, `sessionStorage`에
  노출하지 않는다.
- React·Vanilla UI에 Domain `/api/v1/**`, `/api/v2/**` 경로를 직접 작성하지 않는다.
- Browser 요청은 `window.OmagotchiApi`를 통과한다.
- 인증·Session·JWT·Identity 공통 코드를 Space·Party 연결 때문에 변경하지 않는다.

## 13. 데이터와 오류 처리

- Backend Response를 Source of Truth로 사용한다.
- 공간 목록이 빈 배열이면 정상 빈 상태를 표시한다.
- 파티가 없으면 정상 `party: null` 상태를 표시한다.
- `401`은 기존 Session 만료 흐름에 위임한다.
- `403`은 권한 없음이며 빈 데이터로 숨기지 않는다.
- `404`는 삭제·접근 불가능 Resource 또는 확정 계약상의 미생성 상태로 구분한다.
- `409`는 동시 점유·중복 초대·정원 초과 등 확정 Error Code에 맞춰 안내한 뒤 재조회한다.
- `410` 또는 만료 Error는 점유·초대·연동 만료 상태로 처리한다.
- `5xx`와 Network 실패를 Prototype이나 Browser 저장소 값으로 성공 처리하지 않는다.
- 상태 변경 요청 중에는 중복 조작을 막고, 실패하면 Server 상태를 재조회한다.
- Error 내부 원문을 그대로 노출하지 않고 Server의 사용자용 메시지 또는 공통 메시지를
  사용한다.

## 14. 완료 조건

- 회의실 목록의 Loading·Empty·Ready·Error 상태를 확인했다.
- 내 파티 조회의 파티 있음·없음·권한 없음·오류 상태를 확인했다.
- 입장·반납·연장·참여자·파티 Action이 Backend 성공 응답 이후에만 UI에 반영된다.
- 동시 입장 충돌과 정원 초과를 Server가 판정한다.
- 새로고침·다른 Tab·다른 사용자에서 Server 상태가 일치한다.
- WebSocket/STOMP 없이 BFF Polling으로 다른 사용자의 상태 변경이 반영된다.
- 숨은 Tab, 중복 요청과 반복 실패 상황에서 Polling 호출이 누적되지 않는다.
- API 실패 시 `sessionStorage` Prototype이 성공 상태로 표시되지 않는다.
- 확정된 범위의 업무 상태가 Browser 저장소에 정본으로 남지 않는다.
- 기존 Home Overlay, `/space`, Tab, Dialog, `data-*`, class와 모바일 Layout이 유지된다.
- 실제 Telegram Token이 API JSON, DOM, Clipboard, URL Field와 `window.*`에 노출되지 않는다.
- BFF Controller·Client·mapping·Frontend Action에 대한 테스트와 종단 수동 검증을 수행했다.
- 생성된 Bundle은 Source Build로 갱신했고 직접 수정하지 않았다.
