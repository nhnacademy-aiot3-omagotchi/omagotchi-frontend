# Timer Backend Integration Prompt

> 필수: 이 Prompt를 실행하기 전에
> [Backend Integration AI 공통 보호 규칙](공통-보호규칙.md)을 먼저 읽고 그대로 따른다.
> 공통 보호 규칙과 이 문서가 충돌하면 더 좁고 안전한 수정 범위를 적용한다.

## 작업 목적

기존 Timer UI와 화면 흐름을 유지하면서 Backend Timer API를 연결한다.

이 작업의 핵심은 Frontend Timer를 학습 시간의 정본으로 사용하지 않고, Backend Response를 기준으로 학습 세션 상태와 누적 시간을 표시하는 것이다.

## 작업 지시

아래 지시를 그대로 따른다.

현재 프론트엔드는 이미 화면 틀과 리뉴얼 방향이 정해져 있다.
Home 화면은 React island가 UI DOM을 렌더링하고, 기존 `home.js`가 `data-*` 계약을 기준으로 기능을 연결하는 방향으로 전환 중이다.
따라서 이 작업은 새 화면을 만드는 작업이 아니라, **현재 만들어진 Timer 화면 구조와 React Home island 계약 안에서 Backend API만 연결하는 작업**이다.

### 절대 지킬 것

- 현재 Home React island 구조를 임의로 갈아엎지 말 것.
- 기존 `data-timer-*`, `data-xp-*`, `data-attendance-*` DOM 계약을 깨지 말 것.
- 현재 CSS 구조를 임의로 합치거나 대규모 재작성하지 말 것.
- 현재 JS 모듈 구조를 무시하고 새 흐름을 만들지 말 것.
- 현재 버튼 위치, 화면 이동, 사용자 플로우를 임의로 변경하지 말 것.
- 기존 Home 화면의 캐릭터, EXP, 출석, BGM, 채팅 UI를 Timer 연동 때문에 건드리지 말 것.
- API 연결에 필요한 최소 변경만 할 것.
- UI 변경이 필요하면 기존 클래스와 구조 안에서 상태 표시만 추가할 것.
- Backend API 명세에 없는 기능을 상상해서 만들지 말 것.
- Mock을 새로 만들지 말 것.
- `.storybook/**`, `src/main/frontend/ui/**`, Story 파일과 `css/ui/**`를 수정하지 말 것.
- `GameDialog`, `GameTabs`, Radix UI, Motion과 Storybook 구성을 변경하지 말 것.
- Domain `/api/v1`, `/api/v2` 경로를 React 또는 Timer UI에 직접 작성하지 말 것.
- Browser API 호출은 기존 `window.OmagotchiApi`와 `/bff/v1/**` 경계를 유지할 것.
- `home-app.js` 생성물을 직접 수정하지 말 것.
- Timer 연동 범위를 넘어 인증·Session·JWT·Identity 코드를 수정하지 말 것.

### 작업 방식

1. 현재 파일 구조를 먼저 파악한다.
2. 기존 Timer 관련 DOM, CSS class, JS 상태 흐름을 유지한다.
3. API 호출 함수만 service/helper 단위로 분리한다.
4. Backend Response를 기존 화면 상태에 매핑한다.
5. 성공/실패/로딩/빈 상태만 UI에 반영한다.
6. 테스트 또는 수동 확인 가능한 변경만 남긴다.

## 공통 작업 규칙

- 현재 존재하는 화면, 라우팅, 컴포넌트 구조를 기준으로 API를 연결할 것.
- 화면 흐름을 임의로 변경하지 말 것.
- 기존 UI, 기능 흐름과 DOM 계약을 보존할 것. API 상태 표현에 필요한 최소 변경만 허용한다.
- 현재 리뉴얼된 Home 화면 틀을 유지할 것.
- 필요 없는 리팩터링, 파일 이동, 네이밍 변경을 하지 말 것.
- Backend Response를 Source of Truth로 사용할 것.
- 권한 판단은 Backend에서 수행하고, Frontend는 UX 처리만 담당할 것.
- Backend API 명세에 없는 기능은 구현하지 말 것.
- API 응답 필드명이 기존 프론트 상태명과 다르면 프론트 내부에 매핑 레이어를 둘 것.
- 기존 Mock·Prototype fallback은 API 정상 연동과 회귀 검증이 끝난 범위에서만 제거할 것.
- API 실패를 Mock 또는 Browser 저장소 값으로 성공 처리하지 말 것.
- 새 Mock 데이터를 만들지 말 것.
- 로딩, 성공, 실패, 빈 상태를 모든 API 연동 화면에 반영할 것.

## 금지

- userId 직접 전달 금지
- role/admin flag 전달 금지
- Backend에 없는 데이터 임의 생성 금지
- API 명세에 없는 query parameter 추가 금지
- API 명세에 없는 request body field 추가 금지
- 프론트에서 임의 status 값 생성 금지
- 임시 sessionId 생성 금지
- 임시 startedAt, endedAt, totalStudySeconds 생성 금지
- 성공했다고 가정하고 UI만 먼저 바꾸는 처리 금지
- localStorage/sessionStorage 값을 학습 시간 정본으로 사용 금지
- Timer API 연동을 이유로 Home React island 컴포넌트 구조나 화면 레이아웃을 대규모 재구성 금지
- 캐릭터/EXP/출석/BGM/채팅 UI 수정 금지
- 기존 CSS 파일 구조를 무시하고 새 거대 CSS 파일 생성 금지

## 인증

Browser에서는 Token 원문을 직접 다루지 않는다.

- Browser → Frontend BFF: Same-Origin Session Cookie 기반 요청
- Frontend BFF → Domain Service: Session의 Access JWT를 `Authorization: Bearer`로 relay
- Access Token / Refresh Token을 HTML, JavaScript, localStorage, sessionStorage에 노출하지 않는다.

## 구현 원칙

- 기존 Timer UI 흐름을 유지한다.
- Frontend timer 값만으로 학습 시간을 확정하지 않는다.
- 학습 시작, 종료, 누적 시간은 Backend Response를 기준으로 표시한다.
- Frontend의 Timer는 진행 중 UX 표시용이다.
- 새로고침 후에는 Backend에서 현재 학습 상태를 다시 조회해 UI를 복원한다.
- Timer와 Attendance는 다른 도메인이다.
- 출석 상태를 학습 시간 확정 근거로 사용하지 않는다.
- 퇴실 후에도 Timer 사용 가능 정책이 있다면 Backend 정책과 UI 안내를 기준으로 처리한다.

## 상태 처리

- 초기 진입 시 현재 학습 세션 상태를 조회한다.
- 진행 중 세션이 있으면 Backend의 시작 시각/누적 시간 기준으로 Timer를 표시한다.
- 진행 중 세션이 없으면 시작 가능한 상태를 표시한다.
- 시작 성공 시 Backend Response 기준으로 running 상태를 반영한다.
- 종료 성공 시 Backend Response 기준으로 최종 학습 시간을 표시한다.
- 실패 시 Timer UI를 성공 상태로 바꾸지 않고 오류 메시지를 표시한다.
- null, 빈 문자열, 삭제된 세션, 권한 없음, 만료된 세션 응답을 UI에서 처리한다.

## API 연동 구조

- Timer API 호출은 한 곳에서 관리한다.
- `home.js`에 fetch 호출을 직접 늘리지 말고 service/hook에 해당하는 함수 단위로 분리한다.
- React 컴포넌트는 화면 구조와 상태 표현을 담당하고, Backend API 호출은 공통 API/helper 계층으로 분리한다.
- 기존 Vanilla JS에서 React로 기능을 옮길 때는 Timer 기능 단위로 작게 옮긴다.
- 요청/응답 타입 또는 DTO shape을 명확히 문서화한다.
- 서버 에러 메시지가 있으면 우선 표시하고, 없으면 공통 오류 메시지를 사용한다.
- 화면 렌더링 함수와 API 호출 함수를 분리한다.
- API 응답 DTO와 화면 상태 DTO가 다르면 매핑 함수를 둔다.
- 스타일 클래스명과 API 필드명을 강하게 결합하지 않는다.

## 완료 체크

- Mock 없이 실제 API 응답만으로 Timer 주요 플로우가 동작하는지 확인
- 새로고침 후 진행 중 Timer가 Backend 상태로 복원되는지 확인
- 시작/종료 성공 후 Backend Response 기준으로 화면이 갱신되는지 확인
- 실패 시 사용자에게 명확한 피드백이 보이는지 확인
- 퇴실 후에도 Timer 사용 가능 정책이 UI에 반영되는지 확인
- EXP/레벨 반영은 Backend Gamification Response 기준으로만 처리되는지 확인
- 기존 Home 화면 흐름과 API 계약이 깨지지 않는지 확인
